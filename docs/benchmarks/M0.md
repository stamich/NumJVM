# M0 benchmark results

M0 benchmarks check that the architecture adds no hidden costs. They do not show peak arithmetic throughput: kernels are
scalar Java loops until M2. Read the NumPy columns with that in mind.

## Setup

|          |                                                                                                                                                       |
|----------|-------------------------------------------------------------------------------------------------------------------------------------------------------|
| Machine  | Cloud VM, 2 vCPU Intel Xeon @ 2.10 GHz (shared), 7 GiB RAM, Linux 6.x                                                                                 |
| JVM      | OpenJDK 25.0.4, G1, `-Xmx4g -XX:MaxDirectMemorySize=4g` (set by the benchmarks)                                                                       |
| JMH      | 1.37, 1 fork, 3 × 1 s warm-up, 5 × 1 s measurement, average time, `-prof gc`, 1 thread                                                                |
| NumPy    | 2.5.3, Python 3.13, `OMP_NUM_THREADS=1`, `timeit` best of 5 rounds                                                                                    |
| Commands | `./gradlew :numjvm-bench:jmh -PjmhArgs="<benchmark> -p size=... -prof gc"` and `python3 numjvm-bench/numpy/bench_numpy.py --sizes 1024,65536,1048576` |

Sizes are float64 element counts arranged as a near-square matrix (1,024 = 32 × 32, 65,536 = 256 × 256, 1,048,576 =
1024 × 1024).

## Methodology notes

- JMH measures a warmed-up call from Java; `timeit` measures a call from the Python interpreter, which adds roughly
  50–200 ns of call overhead. Below a few microseconds the comparison is dominated by that difference, not by the
  libraries.
- NumPy's `add` and `sum` loops use SIMD; NumJVM's M0 kernels are scalar. The Vector API path is M2 work.
- `±` is JMH's 99.9 % confidence half-width. On a shared 2-vCPU VM it is wide for anything that allocates megabytes.
- Element-by-element reads (`contiguousRead`, `stridedRead`) have no NumPy counterpart:
  a Python loop over elements measures the interpreter.

Views cost the same at 1,024 and 1,048,576 elements and allocate only their metadata (200–300 bytes): they are O (rank),
as designed. Allocation is the weak spot: Java zeroes and the GC tracks every new array, so `NJ.zeros` is 4–8× slower
than `np.zeros`. Confined scopes avoid most of that cost; prefer them for temporaries.

- **Element access and iteration do not allocate**: under 1 B/op for a full traversal of 65,536 elements through
  `getDouble(i, j)`; the kernels allocate only their result and, for strided inputs, the iterator (about 150 bytes per
  call, not per element). The accessor costs 0.9–1.2 ns per element on any layout.
- **Contiguous kernels are 2–4× slower than NumPy**, the expected gap between scalar loops and NumPy's SIMD loops.
- **Summing a transposed array is 13× slower than NumPy** at 1M elements. NumPy reorders the loops to walk memory
  sequentially; M0's iterator always takes the last logical axis as the inner loop, which strides through memory by a
  full row. This is the loop-reordering work planned for M1 (ADR-003), and the largest single gain available.

## Reproducibility

The subset below was run twice back to back. The target from the M0 plan was ±5 %; on this shared VM **10 of 25 results
met it**. All pairs overlap within JMH's error bars, and allocation per operation is identical between runs, but timings

elements, the F and BROADCASTED layouts and
`scopeAllocation` are covered by the suite but have no results here.
