# M1 benchmark results

M1 benchmarks answer two questions: does the layout of an operand still decide its speed (the M1 exit criterion), and
where do NumJVM's scalar inner loops stand against NumPy's SIMD loops (the input to M2). They are the full matrix of the
four M1 suites, run with three forks.

## Setup

|          |                                                                                                                 |
|----------|-----------------------------------------------------------------------------------------------------------------|
| Machine  | Cloud VM, 2 vCPU Intel Xeon @ 2.10 GHz (shared), 7 GiB RAM, Linux 6.x — no dedicated hardware was available      |
| JVM      | OpenJDK 25.0.4, G1, `-Xmx4g -XX:MaxDirectMemorySize=4g` (set by the benchmarks)                                  |
| JMH      | 1.37, **3 forks**, 3 × 0.5 s warm-up, 5 × 0.5 s measurement per fork (15 samples), average time, 1 thread      |
| NumPy    | 2.5.4, Python 3.13, `OMP_NUM_THREADS=1`, `timeit` best of 5 rounds, run after JMH on the idle machine            |
| Suites   | `UfuncBenchmark`, `ReductionBenchmark` (1,024 / 65,536 / 1,048,576 float64 elements × 5 layouts), `UfuncDTypeBenchmark`, `ReductionDTypeBenchmark` (1,048,576 elements × 7 dtypes): 318 results |
| Commands | `./gradlew :numjvm-bench:jmh -PjmhArgs="UfuncBenchmark\|UfuncDTypeBenchmark\|ReductionBenchmark\|ReductionDTypeBenchmark -f 3 -w 500ms -r 500ms -rf csv -rff jmh-m1.csv"`, `python3 numjvm-bench/numpy/bench_numpy.py --suite m1`, `python3 numjvm-bench/numpy/compare.py` |

The M0 report asked for dedicated hardware and three forks. Three forks were run; dedicated hardware was not available,
so the numbers come from the same shared VM as M0's, and the error column (JMH's 99.9 % half-width over all forks) is
the honest measure of their spread. Where it exceeds a third of the score, read the row as an order of magnitude.

| Criterion (from the 0.2.0 plan)                                   | Measured at 1,048,576 elements           | Result |
|-------------------------------------------------------------------|------------------------------------------|--------|
| Summing a transposed array takes at most 2× a contiguous one       | `sumAll`: 1.06× (C 803 µs, T 854 µs)     | Met    |
| Broadcast add within 2× of contiguous                             | `add`: 1.58×; `addRow`: 0.93×             | Met    |
| Kernels allocate nothing per element (`-prof gc`)                  | see below                                | Met    |

Bytes per call under `-prof gc` at 65,536 elements (1 fork): `add` 526,191 B and `exp` 525,703 B, of which the result
array is 524,288 B; `addOut` (no result to allocate) 1,088 B; `sumAll` 2,297 B; `sumAxis0` 4,504 B, including its
2,048-byte result. The remaining 1–2 KB per call are the iteration plan, the iterator and the result's metadata: per
call, not per element, and the same for the C and transposed layouts.

- **Reductions and unary functions no longer depend on the layout.** `sumAll` over a transposed array is 1.06× the
  contiguous time at 1M elements, against 12.8× in M0: the iteration plan reorders the axes so that the input is read
  sequentially (ADR-004). `exp` and `sqrt` are within 10 % across all five layouts.
- **Binary operations with operands in different orders stay slower**, as in NumPy: when the operands disagree, C order
  wins and the transposed operand is read with a stride. NumJVM's `add` pays 1.3–2.0× for it, NumPy 5.7–6.2×.
- **Two weak spots remain.** `addOut` with a transposed first operand (3.1×) writes a C-ordered `out` while reading the
  transposed input against its grain, and `prodAxis0` on F and transposed inputs (2.5–3.3×) reduces along the
  contiguous axis with the output stride 0, which disables the contiguous path. Both are inner-loop choices, not
  traversal ones, and go into M2's vectorized loops.

## Against NumPy

Selected rows (C layout or per dtype). Ratio = NumJVM / NumPy; below 1 NumJVM is faster.

| Benchmark | Layout / dtype | Size | NumJVM | NumPy | Ratio |
|-----------|----------------|-----:|-------:|------:|------:|
| `sumAll` | C | 1,024 | 1.6 µs | 1.7 µs | 0.95 |
| `sumAll` | C | 65,536 | 45.3 µs | 17.1 µs | 2.65 |
| `sumAll` | C | 1,048,576 | 803 µs | 371 µs | 2.16 |
| `sumAll` | transposed | 1,048,576 | 854 µs | 500 µs | 1.71 |
| `meanAll` | C | 1,024 | 2.5 µs | 2.7 µs | 0.91 |
| `addOut` | C | 65,536 | 41.2 µs | 42.5 µs | 0.97 |
| `addOut` | broadcast | 65,536 | 35.8 µs | 52.5 µs | 0.68 |
| `add` (allocates) | C | 65,536 | 129 µs | 20.7 µs | 6.25 |
| `add` (allocates) | transposed | 65,536 | 163 µs | 128 µs | 1.28 |
| `less` | C | 65,536 | 44.2 µs | 14.6 µs | 3.03 |
| `sqrt` | C | 65,536 | 206 µs | 71.8 µs | 2.87 |
| `exp` | C | 65,536 | 467 µs | 55.6 µs | 8.40 |
| `sin` | C | 65,536 | 763 µs | 493 µs | 1.55 |
| `add` | int32 | 1,048,576 | 3.30 ms | 0.47 ms | 7.03 |
| `sum` | int32 | 1,048,576 | 9.73 ms | 0.45 ms | 21.6 |
| `sum` | complex128 | 1,048,576 | 1.98 ms | 0.71 ms | 2.77 |
| `exp` | complex128 | 1,048,576 | 23.4 ms | 15.7 ms | 1.48 |

- **Writing into an existing array is on par with NumPy** (`addOut`: 0.68–0.97× at 65,536). The gap in `add` is the
  result allocation: a new 512 KiB array costs NumJVM about 90 µs, three times the loop itself, against 20 µs for NumPy
  (the M0 report measured the same 4–8× gap for `NJ.zeros`). Scopes and `out=` avoid it today; M2 should remove the
  double zeroing of fresh native memory.
- **Reductions are within about 2–2.7× of NumPy for floats**, the expected gap between one scalar and NumPy's SIMD
  pairwise loop; at 1,024 elements, where call overhead dominates, NumJVM is level.
- **Integer sums are 20× slower**: int32 is widened to an int64 temporary before reducing (as the result dtype requires)
  instead of accumulating in the loop. A widening reduce loop is a small M2 task with a large payoff; `mean` of int32
  (17×) has the same cause.
- **Transcendental functions follow `java.lang.Math`**: `sin` is 1.5× NumPy, `exp` 8× (NumPy's AVX-512 `exp`), and
  complex functions, which NumPy runs through scalar glibc code, are within 1.5–3×.
- **1M-element results that allocate** have wide error bars (up to ±50 %): each call allocates 8 MiB of native memory
  that the garbage collector releases, and timing depends on when it runs. Use the 65,536 rows, or the `out=`
  variants, for loop speed.
