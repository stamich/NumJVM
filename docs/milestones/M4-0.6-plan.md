# Proposed NumJVM 0.6.0-alpha: fusion and opt-in parallel CPU execution

This is a proposal, not implemented functionality or a release commitment.
The roadmap calls for worker pools and deterministic parallel reductions after
an ownership design. The 0.5.0 reference investigation adds an earlier
priority: correct the large fused-vector allocation and performance problem
before choosing parallel thresholds. See the [results](../benchmarks/M3-1-reference-results.md).

## Scope and design

First reproduce and profile fused ADD and CHAIN from a recorded clean revision.
JFR and JMH point to large allocations around float vector loads; the use of an
array of vector values and per-chunk `evaluate` call is a hypothesis to test,
not a proven compiler diagnosis. Prototype generated loops that keep vectors in
locals, compare alternative designs, and validate allocation and timing on JDK
25. Preserve float32 intermediate rounding, mixed promotion, edge values,
broadcasting, layout, tail and overlap behavior. Reassess both small AUTO
overhead and float64/mixed paths; do not assume a float32 fix generalizes.

Add an explicit opt-in, reusable, bounded worker context after the single-worker
baseline is understood. Existing APIs remain single-worker by default. Start
with eligible contiguous float32/float64 unary and binary ufuncs, expressions,
and full-array sum. Other types, strides, axis reductions, contractions and
matmul use the documented existing single-worker path. Do not modify native
BLAS thread settings or silently nest parallel BLAS work.

Confined `NJ.scope()` memory cannot be passed to workers. Fall back to the
single-worker operation for inaccessible inputs or outputs and retain existing
ownership, alias and errors; do not silently copy to shared memory. Shared
scope access must finish before return. Specify concurrent close, interruption,
nested calls and failure behavior in the ADR and test them against the actual
FFM semantics. Partition writes only when independence is established; preserve
safe identical-view in-place behavior.

For parallel sum, fix chunk boundaries and the combination tree independently
of worker count and scheduling. State the conditions for reproducibility,
including dtype, backend and algorithm version; a parallel result can differ
from sequential floating-point sum. Require tests for NaNs, infinities, signed
zero, empty arrays and rounding, as well as normal numerical tolerances.

Each task is intended as a separate reviewable commit. Research tasks record
findings and a decision; if the stated approach does not work, record the
alternative and evidence instead of claiming a fix.

and reproducible verification. B01 follows A04; C01–C05 follow A05; D tasks
follow the applicable foundation and fusion fixes; E04 and F03 require the
reference campaign and actual-head checks. If an investigation shows that a
specific implementation is unsuitable, its task must document the evidence and
resulting decision.

## Acceptance and benchmarking

Require correct output and existing ownership/alias behavior, bounded resources,
no worker access after return, observable fallback, and repeatable parallel sum
under its stated configuration. Test one and multiple worker counts and close
races. Run JMH on the reference machine with 1, 2, 4, 8 and 16 workers; 32 is an
optional SMT experiment. Record provider, dtype, layout, revision, JDK and native
thread settings, with campaigns run separately. Set numeric parallel targets
after the clean baseline, retain prior 0.5.0 goals and report every gate honestly.

Portable solve/Cholesky and optional LAPACK remain a separately scoped 0.7.0
candidate. General axis reductions, parallel contractions/matmul, arbitrary
layout parallelism and automatic global threading are outside this proposal.
