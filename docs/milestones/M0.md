# M0 — Core array and memory foundation: summary and retrospective

M0 delivered NumJVM 0.1.0-alpha between 1 and 25 November 2025: 44 tasks, one commit
each, across the spike (M-1) and six increments (M0.1–M0.6).

The plan was sized for one full-time developer; the calendar shows the milestone fit in
25 days of mostly evening and weekend sessions. Increments with a precise external
reference (NumPy slicing, reshape, `.npy`) went fastest, because the oracle settled
every question of semantics immediately.

## What changed from the plan

- **The spike overturned analysis finding #4.** Native memory from automatic arenas is
  reserved against `-XX:MaxDirectMemorySize`, and the JDK collects and retries when it
  is reached, so RSS stays bounded. Accounting stayed (for visibility); the soft limit
  became opt-in.
- **Heap threshold raised from 32 KiB to 1 MiB.** Automatic native allocation was slower
  than heap allocation at every measured size (ADR-001).
- **bfloat16 got element access.** The plan made it storage-only, but conversion is three
  lines; only complex remains storage-only.
- **`keep()` landed in two steps**: the byte-level copy in T2.4, the public
  `NJScope.keep(NDArray)` with copies in T3.5, because NDArray did not exist yet when
  the memory phase ran. The plan's dependency list missed this.
- **Indexing every axis returns a 0-D array** (Array API), where NumPy returns a scalar;
  the oracle stores those results as 0-D arrays.
- **Reproducibility target missed.** Two back-to-back JMH runs on the shared 2-vCPU VM
  agreed within 5 % for 10 of 25 results; all overlapped within JMH's error bars. The
  report says so; the next benchmark run needs dedicated hardware and three forks.

## What we learned

1. **Transposed reductions are the largest performance gap**: summing a transposed
   1M-element array is 13× slower than NumPy, against 2× for contiguous data. Loop
   reordering is worth more than any SIMD work and belongs at the start of M1.
2. **Allocation, not arithmetic, dominates small operations.** `NJ.zeros` is 4–8× slower
   than `np.zeros`; confined scopes close the gap. M1 kernels should accept an output
   array or allocator.
3. **A NumPy oracle with committed fixtures pays for itself.** It found one semantic
   difference (0-D vs scalar) and confirmed byte-identical `.npy` output, without
   making the normal build depend on Python.
4. **Layouts must be constants for the JIT.** Passing a `ValueLayout` as a parameter cost
   10× in the spike; every kernel uses `static final` layouts.
