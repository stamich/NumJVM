# M1 — Elementwise engine: summary and retrospective

M1 delivered NumJVM 0.2.0-alpha between 28 November 2025 and 6 January 2026: 42 tasks, one commit each, in a quality
baseline (Q1–Q6) and six increments (T1–T6).

## What changed from the plan

- **The oracle found real bugs, not only regressions.** The ufunc × dtype × layout matrix showed that operands
  converted before a loop were copied in C order, so results of mixed-dtype operations on Fortran-ordered inputs came
  out C-ordered; Hypothesis-drawn cases showed that NumPy's float16 `maximum`/`minimum` break ties the other way round
  from float32/float64. Both were fixed in the tasks that found them.
- **NumPy's results depend on the CPU in places.** A fixture built with `np.exp2` differed by one ulp between the
  development machine and the CI runner (AVX-512), and NumPy's SIMD complex multiply fuses multiply-adds. Fixture inputs
  are now built from exact operations only, and complex products are tested on values whose products are exact.
- **`mean` divides by an intp, not a weak scalar.** Matching NumPy bit for bit required dividing float32 sums in
  float64 and complex64 sums in complex128 before rounding back.
- **Complex rounding is per part** (`PyArray_Round`), not complex multiplication by a power of ten.
- **Scoped results (T4.7) came in as a task of their own**, because every operation needed an allocator decision.
- **Dedicated benchmark hardware was again not available.** The full matrix ran with three forks on the shared VM;
  the report states it and gives JMH's error for every row.
- **SonarCloud**: the CI analysis, gate and coverage are in place, but the project's Automatic Analysis setting has to
  be switched off by the owner before the first CI analysis is accepted. Dependabot was dropped for now at the owner's
  request; action SHAs are updated by hand.

## What we learned

1. **Loop order beat SIMD.** The iteration plan alone took the transposed sum from 12.8× to 1.06× of contiguous; no
   vector code was needed. The remaining layout gaps are inner-loop choices (`addOut` against the grain, reductions
   along the contiguous axis), not traversal.
2. **Allocation dominates simple ufuncs.** `add` into an existing `out` is on par with NumPy; allocating the result
   makes it 6× slower at 64K elements. M2 should reduce allocation cost before vectorizing `add`.
3. **Widening temporaries are expensive.** `sum(int32)` converts the whole array to int64 first and is 20× slower than
   NumPy, which widens inside the loop. Mixed-type loops belong in M2.
4. **Generated loops scale.** About 580 loops from a table of expressions and seven templates kept every dtype and path
   consistent; the oracle and `LoopPathsTest` cover all of them.
5. **An exact oracle needs an explicit accuracy contract.** D6's ULP tolerances let `java.lang.Math` stand in for
   NumPy's libm without weakening the exact checks everywhere else.
